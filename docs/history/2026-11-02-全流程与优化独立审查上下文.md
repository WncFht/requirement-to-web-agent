## 老师的任务与不可削弱的标准

当前 `input/` 已恢复老师 ZIP 的原始字节，记录在 [input/source.json](../../input/source.json)。`requirements.yaml` 的 SHA256 为 `54db4df5b11b5e88d97ff7726c8abc93d55e9d0124f04f23c85fef20ff8d94ee`。历史 pending 扩展位于 `examples/registration-pending/`，不能与原版混算性能。

- 首页 `/`：未登录显示 Register、Login；已有有效会话应恢复准确用户名并隐藏入口；未知会话只读拒绝；查询中或失败时不能显示过期身份。
- 注册 `/register`：完整旅客字段、Vietnam、Male/Female、精确标签、密码隐藏、条款勾选；成功保存数据与密码哈希、创建可用会话并返回首页，刷新仍登录；重复用户名报错且不改数据库，用户名按精确值比较。
- 登录 `/login`：正确用户名和密码只创建会话，不修改账户；错误密码报错且无写入；输入名称、placeholder 和 LOGIN 按钮与老师契约一致。
- 参考布局需要另外检查，自动化行为通过不等于像素或视觉相似度已签收。

完整成功必须包含编译器原有 typecheck、后端契约测试、UI 存在性检查、生成 E2E、构建，以及老师 4 条原测试＋独立固定 10 条检查；还要对生产构建启动后的应用再执行同样 14 条，无 skip/flaky。模型生成的测试数量可变，其全绿不能代替固定覆盖。

固定契约是 [acceptance/contract.json](../../acceptance/contract.json) 的 v2；曾在最新实验之前纠正“会话查询失败时必须显示入口链接”的过度约束，保留无过期身份要求。老师测试未修改，历史断言版本和负例保留。审查者应同时核对独立验收适配器，不能默认它绝对正确。老师原测试文件名中的 REQ-1/REQ-2 对应注册/登录，与 YAML 的 REQ-2/REQ-3 不同。

禁止靠跳过测试、改弱断言、改老师输入、硬编码测试用户或直接手修失败产物获得 GREEN。冻结后测试不改；语义性编译器修改要有决策记录、回退开关和新输出目录验证。原失败目录、`.env` 和生产数据库不得被覆盖。

## 编译器全流程

入口是 `main.py → run_all.py → 00–12`，共享输出目录的 `.arc/*.json` 中间表示（IR）。`main.py` 最后还执行数据库初始化与生产构建，并写部署入口。

| 阶段  | 工作与主要产物                                       | 性质                                     |
| ----- | ---------------------------------------------------- | ---------------------------------------- |
| 00    | npm workspace、React/Express/SQLite 脚手架           | 确定性                                   |
| 01    | 需求树、场景及截图分析：requirements/visual_analysis | 模型＋校验                               |
| 02    | 数据库实体、字段、关系：db_schema                    | 模型＋校验                               |
| 03–04 | 字段级读写义务：db_obligations；引用/守恒检查        | 03 模型，04 确定性                       |
| 05    | SQL、初始化实现                                      | 模型生成文件                             |
| 06–07 | API 分解及前置/后置条件（P/Q）                       | 模型＋集合/形状校验                      |
| 08    | 先生成测试并冻结，再实现后端直至 GREEN               | 模型有界修复＋真实测试                   |
| 09    | 页面、元素、绑定、fixture、可见谓词设计              | 增量模型设计＋检索＋校验                 |
| 10    | 从设计生成 UI 存在性断言，再实现页面                 | 断言生成代码＋模型实现                   |
| 11    | 触发器、事件、调用义务与事件契约                     | 模型＋校验                               |
| 12    | 按需求生成/冻结 E2E，逐事件创建，终验全量修复与回归  | 模型有界修复＋真实浏览器/后端/隔离数据库 |

`FileWorkspace` 管理可写文件和只读参考，模型返回整文件 `edits`；路径、越界、软链和权限由确定性代码检查，写入异常会回滚。`run_file_agent` 负责编辑→检查→反馈→重试，通常最多 18 轮。请独立检查 gate 失败后的工作区语义，不要把“写入原子回滚”误解为“全部失败提案都事务回滚”。

数据库/API/交互的字段读写集合守恒可以发现漏分配或多分配，但不能证明自然语言义务推断正确，也不能证明 Cookie 等跨接口协议兼容。08/12 由模型生成测试，同模型或另一次调用的审阅也不是独立正确性证明。09 错误的 IR 会被 10 确定性编译成错误但看似合法的冻结断言，后续实现可能无法同时满足真实需求。

创建、终验和测试生成的文件权限不同。单事件收窄创建只授权新 handler，最终修复保留较广的前端文件；后端和冻结测试不归前端修复循环所有。某些后端/IR 缺陷会让前端反复 18 轮仍无法正确修复。

## 最新 12 次串行四组合实验

测量提交固定 `e910eed`；每配置 3 次，三组内按预先登记顺序串行；同一老师输入/断言、Node22.23.2 和 4,030 项依赖快照。模型为 `deepseek-flash`，通过配置的兼容代理调用，不能由别名推断确切后端模型。关闭思考、传输额外重试 4 次，禁用 E2E 复用，强制 UI 全新设计。生成预算 1200 秒，独立固定及生产验收各 900 秒；首次失败就停止该次后续阶段，失败不替换。

所有尝试预置相同暖依赖，依赖准备单独计时，流水线原有安装检查保留。主试验没有本地重叠模型生成；服务端负载、缓存保留、路由和模型生成轨迹仍不可固定。不是相同随机轨迹的逐步执行对照，也不是多任务泛化验证。

## 缓存 V2 与 14 次生成的全部结果

主实验完全结束后，固定候选 `d236d5d`：先 12 组成对回放，另有每臂一次独立预热；随机命名空间、交错顺序、JSON 字段和值保留，响应重过原 Stage11 契约结构校验。V1/V2 输入分别 46,321/46,309 token，排序可能改变 tokenizer 边界；命中 29.8%→87.1%，未命中 32,497→5,989，输出 1,354→1,467，累计请求 20.69→21.57 秒。局部复用改善但未提速，不能替代应用验收。

之后 V2 两次完整生成 0/2:1,749,451 token/758.5秒和181,480 token/172.0秒，合计1,930,931 token；全流程加权命中 52.5%，无成功应用可比较。V2 保持默认 0、提案仍 proposed。第二次早于 V2 生效阶段失败，不能归因于 V2；这也使整批命中不适合当作纯排序效果。

## 已定位缺口与希望重点挑战的方向

以下是候选研究方向，不是已实施或已证明会有效的修复：

- 跨 API 会话组合：单 API 后端 GREEN 仍可能接受互不兼容的凭据。Cookie producer 名称观察只证明浏览器存了什么，不证明 consumer 能读取。需考虑在后端冻结前执行注册/登录→真实 Cookie→查询→刷新组合验证，或建立通用传输契约；别在前端偷改 Cookie 迎合错误后端。三个错配反例已用实际后端处理器＋隔离 stub 数据库确认读取分支，尚不是修复后的端到端证据。
- 测试生成与冻结：有 RED 不等于测试可满足。未设凭据却要求登录、最后选 Male 却要求 Female，后续实现按正确业务做也会失败。请判断该加结构化动作/状态表示、确定性检查、独立审阅还是其他机制，以及新增成本和误拒风险。
- UI 设计状态：visible 谓词反向、对特定用户名判等、缺绑定初值，会被确定性存在性测试固化。请检查设计 schema 表达能力、fixture 覆盖、跨状态不变量与错误诊断，而不只增加 prompt 例句或替缺失值补零。
- 外部验收语义：页面实际显示用户名仍可能因重复节点不满足老师定位。需要判断设计阶段是否充分接收原测试，以及如何兼顾需求本身、可访问性和外部定位约束，不直接改老师 selector。
- 修复权限与调度：错误处在后端、设计 IR 或冻结测试时，当前前端 18 轮预算可能无法修复。应如何识别缺陷所有者、带证据回到上游并失效下游？与测试冻结、回归和义务守恒如何协调？
- 性能策略：整文件重发、最终全量修复、逐事件全回归、重复安装/构建等可能是成本源。是否先做更好的错误定位、按依赖保护的局部编辑、共享契约、确定性简单事件生成或选择性检查？均须保留最终独立验收，不以缩短失败为成功加速。
- 缓存和反馈：测量真实稳定前缀、首次编辑与修复分布；缓存比率、输入量、未命中输入、输出 token 和实际交付成本分开报告。压缩反馈是否破坏根因线索、结构化报告是否仍重复、provider 路由是否可观测？
- 恢复/并行：目前成功前缀与全工作区指纹保守失效，尚无最小 DAG 重建。阶段有状态依赖和共享源码所有权，不能直接把所有阶段并行作为低风险优化。

下一轮建议应说明其通用性边界和最低验证成本。最新数据只覆盖一个登录任务，尚没有多任务/多模型泛化实验、充分重复次数、视觉签收、完整状态机正确性证明或已修复上述缺口的新固定提交复测。137 项编译器单测、46 项维护测试通过是局部工程证据，不代表应用生成成功率高。

历史还有空名称 Cookie 反例：实际 Chromium 可以存储并恢复该后端会话，测试却误设凭据名称。因此“空名称”与“名称未知”必须区分；不能用强制非空名称或某个固定名称掩盖协议不一致。传输重试还叠加 SDK 自身重试，审查预算时应一并考虑等待时间，不能只看外层次数。
