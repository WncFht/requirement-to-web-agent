# 编码智能体候选验证计划

日期：2026-11-02，Asia/Shanghai。状态：proposed，未启动新模型请求。本文定义未来候选验证与对照实验，不是实测报告。代码边界和 M0–M6 归[实施计划](../2026-11-02-简洁编码智能体实施计划.md)，既有负结果归[历史串行消融](2026-11-02-串行消融与缓存验证.md)。开始登记首个实验协议时复查本文，实际结果另行归入对应报告。

## 研究问题与比较单位

主问题是：简洁编码智能体能否在同一需求、模型、环境、资源预算和验收下，提高完整交付率，并降低包含失败的模型成本？一次从新目录开始的完整尝试是统计单位；模型调用、测试用例和编辑轮次不作为独立重复。

| 比较      | 源码与范围                                                          | 可以支持的结论                                   |
| --------- | ------------------------------------------------------------------- | ------------------------------------------------ |
| 历史结果  | e910eed 的 12 次、d236d5d 的两次                                    | 定位旧流程反例与估计预算，不作为新候选的同期对照 |
| A：legacy | 完整 SHA `e910eed1c3debc779d9308205e274f9b677ececf` 的干净 checkout | 已有流水线的同期表现                             |
| B：coding | M1–M4 完成后封存的候选完整 SHA，显式 `ARC_AGENT_ENGINE=coding`      | 整套候选架构的表现，不能归因于某一项局部优化     |

这轮只比较 A/B，不同时开展模型选择、上下文开关与缓存排序的多因素试验。候选可能同时改变工具、上下文与调度，因此先报告整体取舍；确认有效后才考虑一次改变一个机制的消融。

## 零付费前置验证

M1–M4 全部完成才允许把模型生成列入待执行清单。编译器检查、假模型和本地浏览器不需要真实模型请求；测试使用临时副本和隔离数据库，历史目录与冻结测试原件不动。

| 反例组          | 最小验证                                                               | 必须出现的结果                                           |
| --------------- | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| 文件工具        | 越界、软链、大小写别名、过期哈希、重复片段、批次中途写入失败           | 写入拒绝或原字节回滚，错误和文件身份可追溯               |
| JSON 与模型传输 | 根对象提前闭合、空对象缺字段、`finish_reason=length`、拒绝、超时和限流 | 不截取部分响应作为成功动作；重试受统一预算限制           |
| 门禁            | 全 skip、todo、预期失败、flaky、零测试、损坏报告、服务启动失败         | 均不能 GREEN；预期业务 RED 与基础设施失败分开            |
| 测试准入        | 缺浏览器凭据的已登录正例、Male/Female 矛盾                             | 冻结前定位错误；冻结后发现则 INVALID_TEST，不改断言通过  |
| 真实交互        | Cookie producer/consumer 不一致、form owner 为空、重复精确文本         | 浏览器证据指向真实故障；不能只看 handler 文件名          |
| 读取故障        | 旧身份存在时的 HTTP 503、传输拒绝与重新进入页面                        | 断言状态清空和页面结果，不能仅证明 handler 不抛异常      |
| 循环控制        | 脚本化模型先修后端、再修前端；重复错误与有效进展交替                   | 跨层修改可执行，实际全回归决定完成；有效进展不被错误止损 |
| 中断与证据      | 模型中断、检查超时、缺 usage、重复 response、运行后修改源码            | 终态与未知成本保留，审计明确 INCOMPLETE/INVALID          |
| 平台包          | 在空目录解压，只注入地址/Key/PORT，使用本地假兼容接口                  | 默认模型可用，输入输出实参有效，所有必要模板与模块在包内 |

已有 137 项编译器测试和 46 项维护测试继续执行；新增测试按实际能力选择。通过这些测试只说明本地工程条件具备，不代表模型生成能力或平台成绩。

### 独立评估等价性

1. 原字节复制老师四条与固定十条断言及夹具，核对测试文件、用例身份和哈希；不修改 selector、期望与种子语义。
2. 选择一个已有完整成功应用，在临时副本上分别运行旧入口和候选薄评估入口，两者均须得到相同的 14 条通过、无 skip/flaky/运行器错误。
3. 分别在临时副本引入 Cookie 错配、重复用户名节点和数据库额外写入；双方都应拒绝对应行为，记录原始 reporter。
4. 生产构建使用同一批断言和隔离数据库再次验证，不能用开发服务器通过代替生产通过。
5. 新入口读取真实 CheckResult，旧入口读取真实阶段报告；任何一方缺门禁证明都不通过。不得使用 `--allow-incomplete` 或合成 GREEN 抹平差异。

评估适配信息仅定位真实 schema、路径和凭据名称，不能定义预期结果。新入口及适配器源码也封存在评估版本中；两个架构的断言原件一致。对照模型只接触任务本来提供的材料，项目独立固定十条不作为智能体的额外提示或迭代反馈。

## 实验分层与固定次数

每层单独登记，完成一层不自动启动下一层。真实生成仍受当前“不得自动付费生成”的约束；执行前需要已有授权覆盖所登记的预算和次数。

| 层次             | 拟议规模                                             | 作用与限制                                                       |
| ---------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| P0：离线验证     | 上述反例及所有必要工程检查                           | 零模型请求，修复评估与工具缺陷                                   |
| P1：候选可运行性 | 同一候选提交两次全新生成                             | 只定位运行和打包问题，失败不替换；即使 2/2 也不证明稳定或提速    |
| P2：同期架构筛查 | 登录任务四个配对区组，每组 A/B 各一次，共八次        | AB/BA 各两组，具体顺序在运行前随机登记；只作小样本筛查，不切默认 |
| P3：确认与泛化   | 新协议至少十个配对区组；另加一个预先冻结的非登录任务 | 固定候选后重新验证，不与调参或 P1/P2 混算；仍报告小样本不确定性  |

非登录任务建议选“创建记录→列表/详情→刷新持久化→非法输入无写入”的小型 CRUD，用它检验是否脱离登录特化。验收从该任务需求独立制定，预先冻结；它不是平台六任务的替代。正式综合提交仍需同一源码版本完成平台全部任务，尚无这些结果时不能宣称六任务泛化。

P1/P2 失败后可以修候选代码，但原试验保留失败终态；新提交使用新协议。P3 的候选 SHA 和任务集封存后不再调整。若发现编译器或评估器缺陷，中止并保留该批，说明受影响范围；不可修改后继续沿用原分母。

## 协议、目录与环境

实际执行前生成不可覆盖的 `protocol.json`，所有预算字段必须具体填写；本文不授权任何付费金额。清单至少包含：

- A/B 完整提交号、干净状态、被执行脚本和评估器哈希，必要的 SDK/Python/Node/浏览器版本。
- 输入全部文件、独立断言、模板及包文件哈希；参考图原件一致。
- 模型名、端点、思考设置、输出上限、SDK 与外层重试策略；记录可见的返回模型名与请求 ID，不假定别名等于固定后端版本。
- 相同依赖锁和暖依赖准备策略、宿主与串行策略；每次输出拥有独立可写依赖副本，不能共享可变 Vite cache。
- 运行前登记的完整顺序、次数、授权总预算、每次生成/检查/验收超时和资源限制。
- 预算耗尽、未知用量、超时、服务故障与人工中断的分类和停止规则。

为与历史诊断接近，P2 可沿用生成 1200 秒、固定验收和生产验收各 900 秒的本地超时，登记后两臂一致。这些是建议实验参数，非平台承诺。总 token/调用预算要根据已授权额度在协议里固定；模型请求预留输出余量，返回用量超预算的最后一次调用也计入，未知用量不能当作免费余额继续生成。

不为“公平”强行把两种架构的自然轮数或生成测试数量做成一样。相同外部预算与验收，内部策略差异本来就是架构比较的组成部分；重试配置不同则单列为候选差异，不宣称纯调度消融。

```text
../work/coding-agent-<campaign-id>/
  protocol.json
  sources/A/                       # 固定提交的只读受测 checkout
  sources/B/
  runs/<attempt-id>/
    experiment.json                # 登记身份与各阶段起止
    output/                        # 传给 main.py 的全新输出目录
      .arc/agent/                  # B 的生成记录；A 保留原生记录格式
    fixed/                         # 独立验收原始证据
    production/
    result.json                    # 汇合 generation 与外部验收，不覆盖原件
  analysis.json
  audit.json
```

历史目录和生产数据库不复用。原始源码 worktree 不随实验修改，不包含 `.env`；凭据只由生成器环境注入。共享外部实验器分别读取 A 的原生模型/阶段日志和 B 的事件记录，产出相同的派生指标；不重写 A 的原始文件。源码与日志正常封存后，再允许按现有归档规则清理可重建依赖。

## 成功口径与统计

完整成功要求：生成正常退出、所有内部门禁有真实 GREEN 证据、固定验收全通过、生产验收全通过、无跳过/预期失败伪通过/flaky/运行器错误，且受测代码与冻结测试哈希一致。模型的 `finish` 只产生请求，`INTERNAL_GREEN` 也不等于完整成功。

生成失败且未执行外部验收时，完整成功为 false，外部通过条数记未观测，不伪造为 0/14。可在另一个诊断副本执行固定测试定位缺口，但不把诊断或手动后续修复并回原次成功，也不并入原次 wall time。

| 指标           | 计算与解释                                                                       |
| -------------- | -------------------------------------------------------------------------------- |
| 完整成功率     | 完整成功次数 / 全部登记尝试；报告 Wilson 95% 区间与失败类别                      |
| 测试通过条数   | 有实际执行证据时报告原始数量，分开发与生产；生成测试数另列                       |
| 全部尝试成本   | SDK 返回输入、缓存命中/未命中、输出 token，以及完整 wall time，包含失败          |
| 每成功应用摊销 | 全部已知 token 或 wall time / 完整成功数；无成功时未定义，不记零或稳定无穷大收益 |
| 成功条件成本   | 只看成功尝试的次级描述；不替代失败摊销，不据此排名全部架构                       |
| 调度与修复     | 首次编辑、后续修复、工具读取、测试准备、各检查耗时、有效改动和无进展次数         |
| 缓存           | 对 input token 加权，首次调用和反复修复分开；不追求固定命中率门槛                |
| 不确定性       | 缺失 usage、无结束事件、HTTP 未知计费和未固定的 provider 路由独立列出            |

输入缓存不是实验处理因素；服务端缓存、负载与路由不能固定，不声称冷缓存一致。配对顺序减小时间偏差，不能消除生成随机性与跨次缓存影响。四组筛查只报告各组原始差异和探索性统计；不得把调用数当重复数，也不得用一个有效成功配对计算置信区间。

确认实验按尝试和区组报告完整结果。总耗时包含生成、最终构建及已执行的独立验收，依赖快照准备另列；失败早停降低时间时，明确它没有带来成功交付加速。模型金额只有取得适用价格/账单证据时才单独计算，不从 token 总量直接换算。

## 审计与默认版本决策

审计器独立重算 SDK 用量、模型与检查事件、原始用例结果、退出码和哈希；不能只比较 result 与 reporter 的汇总字段。检查请求/响应配对、重复响应、必需 usage 字段、所有应用源码/冻结测试/配置和原始日志的封存哈希，核对时间顺序与所属进程已结束。缺失证据使审计不完整，不能以缺字段默认为零获得通过。

上线候选至少满足：所有离线反例、评估入口等价、真实上传包验证、当前登录完整固定与生产验收、确认实验、一个非登录任务及源码备份恢复验证。确认试验中候选完整成功次数不得低于对照，失败摊销 token 应更低；时间、失败类型和区间一并审查。二者都无成功、用量不完整或指标互相冲突时不自动晋升。达到这些筛查条件仍不证明总体成功率达到某个百分比。

默认切换是单独的可回退提交，记录原默认、候选 SHA、包哈希、实验协议与限制。P1/P2 只完成筛查，不能移动已验证标签、重写历史数字或将 proposed 改为 implemented。发现新架构没有收益时保留 legacy 默认，并根据反例决定修复候选或拒绝提案。
