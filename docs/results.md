**内部通过没有解决原始需求到最终验收之间的缺口。** 注册页设计为 `prop.label="*Nationality:"`，页面原样绑定 label；内部 UI 断言检查这个生成期望并通过。教师入口却要求 `getByRole('combobox', { name: 'Nationality', exact: true })`，开发与生产都在此停止。原始期望不能为了兼容生成页面而放宽。

另一处覆盖缺口是性别控件：模型返回 `type="radio"`，当前校验与确定性生成器只处理 `type="input" / input_type="radio"`；因此本轮 9 条 UI 测试没有性别控件断言。生成 E2E 确实以真实 `.check()` 选择 Female，但这不能代替未选、切换、fixture 与最终 UI 回归的完整覆盖，不能将这轮 UI GREEN 宣称为 baseline radio 问题已经得到完整验证。

这轮的价值是明确定位下一步：**在设计准入处拒绝未支持类型，并让必需控件的可访问名称依据原始需求，而非仅依据模型自己的设计。** 下一轮仍保留冻结边界与累计回归；先离线复现这两个反例，再按[累计计划](redesign.md#iterations)推进。单次更高 token 不证明改动导致成本增加，单次内部通过也不能估计稳定成功率。

证据位于 gitignored 的 `work/compiler-iterations/`：`round-01/` 原始应用与模型审计、同级 `.conditions.json`/`.run.json`/`.usage.json`/`.result.json`、`.evaluation.json` 和两种模式 `.log`。包 SHA-256 为 `f4fd0fcb3464ace1c1e50f77ef46cc15883ae30ac4ab1e9ec140b7ae77c2914f`。缓存按 SDK 的 `prompt_tokens_details.cached_tokens` 汇总，旧工具仅识别提供方平铺字段，已修正统计并增加回归，原调用日志不变。
